# 見送った六つの判断、再検討

「やらないと決めたこと」の一覧のうち、他はすべて着手する。この六つだけは保留
してある。時間がなかったからではなく、それぞれに理由を書いて断ったからだ。
CLAUDE.md の第一のルールは、決着した判断を変えるには明示的な議論が要る、静かな
リファクタリングで済ませてはならない、というものである。

この文書がその議論にあたる。一項目ずつ判断できるように並べた。それぞれについて
——当時の理由、覆した場合の代償、そしてそれが製品の主張に触れるのか単なる利便性
の話なのか。

**ここでは何も変更していない。** それがこの文書の趣旨である。

（英語版: `reconsidering.md`。内容は同じ。）

## 1. お知らせのオフライン閲覧

> 最初に要望される機能であり、この文書の冒頭にあるルールを破ってしまう唯一の
> 機能でもある。 — `pwa.md`

**当時の理由。** ルールとは、Service Worker はシェルだけをキャッシュし、意味を
持つものは一切キャッシュしない、というもの。キャッシュされた一覧を現在のものと
して見せることは「運転手が昨日の指示を今日のものだと思って読む」ことにあたる。
この一文は、製品の主張をキャッシュに当てはめたものそのものである。

**覆す代償。** コードは多くない——Service Worker にはすでにキャッシュがあり、
クライアントには TanStack Query がある。代償はすべて画面側にある。`pwa.md` が
条件を明記している。キャッシュされた内容は**取得時刻を、画面上に、毎回**表示
しなければならない。控えめなバッジではなく、読み手が見落としようのない一行と
して。しかも「毎回」は将来のレイアウト変更を生き延びる必要があるので、誰かが
付け忘れられるラッパーではなく、お知らせを描画するコンポーネント自体に属する。

**主張に触れるか。** 触れる。しかもこの六つの中で唯一、**きちんとやれば今のまま
より誠実になる**項目である。地下で電波の届かない運転手は、いま何も見られない。
昨日の勤務表を「取得 昨日 18:32」と明示して見せるほうが、何も見せないよりよい。
**ただし**その表示が見落としようがなく、かつオフラインでの確認（確認ボタン）が
不可能なままであること——これはすでにそうなっており、E2E テストもある。

**推奨：やる。** 画面上の取得時刻を必須要件とし、それが無ければ落ちる E2E テスト
を付ける。六つの中で最も覆す価値が高い。

## 2. 連続失敗によるアカウントロック

> レート制限は推測を遅くする。しかし本人を自分のアカウントから締め出すことは
> 決してない。勤務表の掲示板にとっては、そちらのほうが悪い失敗である。
> — `security.md`

**当時の理由。** ロックは可用性の問題を、誰でも引き起こせるサービス妨害に変えて
しまう。同僚のメールアドレスを入力して五回間違えるだけでよい。人がいつ働くかを
伝えることが仕事のソフトウェアにとって、朝五時にログインできないことは、ロックが
防ぐ攻撃より悪い。

**覆す代償。** 実装は小さい。ただし慎重に設計しないと上記の攻撃を招き入れる——
アカウントではなく**送信元アドレス**をロックするか、管理者による解除を必要と
するか。後者は、その管理者が寝ているかもしれない。

**主張に触れるか。** 「当たり前のことが、当たり前にできる」に触れる。入れない
アカウントはその正反対である。

**推奨：現状維持。** ログインはすでに 15 分あたり 1 アドレス 10 回で拒否し、それ
はテスト済みである。さらに何かするなら、誠実な追加はロックではなく、**繰り返しの
失敗を本人に通知する**ことだろう。

## 3. HTTP 経由のバックアップ

> アプリケーションを通して全ダンプを流す口は、データベース全体を返す
> エンドポイントである。どんな権限チェックもそれに見合わない。 — `backup.md`

**当時の理由。** そのエンドポイントは、一度のリクエストですべてを持ち出せる——
パスワードハッシュ、全メッセージ、全添付。認可のバグ一つ、盗まれた Owner
セッション一つ、漏れた API トークン一つで、全部が一回の呼び出しで失われる。今の
設計はホストへのシェルアクセスを要求する。

**覆す代償。** 実装は容易で、リスクは恒久的である。

**主張に触れるか。** 主張というより安全姿勢に触れる。ただし非対称性に注意
——この機能が運用者に節約させるのは `docker compose exec` 一回であり、失敗した
ときに失うのは全部である。

**推奨：現状維持。** 「組織が自分のデータを持ち出せる」を端末なしで実現したいの
なら、より安全な形はすでにあるお知らせごとの CSV 出力であり、データベース全体を
返すエンドポイントで置き換えるのではなく、そちらを拡張することだ。

## 4. バックアップ書庫そのものの暗号化

> 運用者がすでに安全に保管しなければならないファイルを守るために、失う可能性
> のある鍵をもう一本増やすことは、問題を解決せず移動させるだけである。
> — `backup.md`

**当時の理由。** 書庫は `ENCRYPTION_KEY_CURRENT` を意図的に含めていない。書庫を
暗号化すると、同じ「失えば終わり」の性質を持つ鍵が二本目として現れる。鍵を失う
運用者は両方失う。

**覆す代償。** 中程度。誠実な形は新しい鍵ではなく **age / GPG 対応**である。
運用者がすでに管理している公開鍵に対して暗号化すれば、このプロジェクトが失い
うる秘密を一つも持たずに済む。

**主張に触れるか。** 触れない。純粋な工学上の取引であり、主張は絡まない。

**推奨：やる。ただし「あなたがすでに持っている鍵に対して暗号化する」形だけ。**
鍵をここで生成も保管もしない。`pnpm backup --encrypt-to <相手>` が `age` があれば
それに委ね、無ければはっきり断る。

## 5. 通話画面の埋め込み

> 埋め込むということは、ベンダーの SDK が全ページに乗るということであり、
> 差し替え可能なプロバイダという仕組みがまさに避けようとしている囲い込みで
> ある。 — `calls.md`

**当時の理由。** 通話は意図的に「メディアはプロバイダが運び、それ以外はすべて
Atarimae が運ぶ」という形をとっている。SDK の埋め込みはこれを逆転させる。ベンダー
の JavaScript が掲示板の全ページで動き、プロバイダの差し替えは設定変更ではなく
なる。

**覆す代償。** M6a で確立したばかりの CSP を緩める必要も出る。`frame-src 'none'`
と `script-src 'self'` はどちらも `security.md` に理由が書かれており、frame の
ほうはクリックジャッキングから「確認」を守っている。

**主張に触れるか。** 二重に触れる。プロバイダ非依存性と CSP の両方。

**推奨：現状維持。** 別ウィンドウが開くことが実際の不満なのであれば、それは
ウィンドウ管理の問題であり、SDK の埋め込みよりましな答えがある。

### 上の判断のどこが誤っていたか——結局やった

誤りは二つ、そしてその二つで代償のほとんどが消えた。

**上の段落は二つのディレクティブを混同していた。** 「frame のほうはクリック
ジャッキングから確認を守っている」のは `frame-ancestors`、つまり _こちらを_
枠に入れてよいのは誰かという指定である。埋め込みに必要なのは `frame-src`、
つまり _こちらが_ 何を枠に入れてよいかという指定のほうだ。確認を守っている
防御は動かない。動いたら落ちるテストを追加した。

**そして iframe は SDK ではない。** 会議室 URL を枠に入れるだけなら、この
オリジンで第三者の JavaScript は一行も動かない。だから `script-src 'self'` も
動かさずに済む——`calls.md` の反対意見は、押し切ったのではなく回避された。
プロバイダ非依存性も無傷である。このコードベースにベンダーのものは今も何一つ
入っておらず、差し替えは今も設定変更のままだ。

実際に動いたもの：`frame-src` にオリジンが一つだけ増え、`Permissions-Policy`
がカメラとマイクを **そのオリジンにのみ、このオリジンには決して** 許可する。
どちらも `url` 方式のプロバイダで管理者がチェックを入れない限り無効である。

予想していなかった代償：ブラウザーは、枠がプロバイダに拒否されたのかどうかを
ページ側に **知らせる手段を持たない**。だから検出はできず、管理者が明示する
しかなく、真っ白な枠から抜ける道を画面に常に置く必要がある。さらに、埋め込んだ
会議室は会話を移動すると閉じる——ウィンドウは閉じなかった。どちらも取り繕わず
`calls.md` に書いた。

**作ったうえでの推奨：やる。ただしプロバイダごとの任意設定として。**
既定はウィンドウのまま、抜け道は常に画面に。

## 6. 悪意ある管理者への対策

> Owner はすべてを読め、すべてを変更できる。監査ログはそれを行った事実を記録
> するが、それは防止とは別の保証である。 — `security.md`

**当時の理由。** ここでの「防止」はエンドツーエンド暗号化か複数人承認を意味する。
どちらも大きく、どちらも製品と衝突する。お知らせを読めない Owner は掲示板を管理
できないし、小さな会社に朝五時のシフト変更を連署できる二人目はいない。

**覆す代償。** 非常に大きく、製品そのものが別物になる。

**主張に触れるか。** 触れる。「管理者が管理者を追加できる」は表看板に書いてある。
自分の管理者を信用しないシステムは、別の製品である。

**推奨：現状維持。** そのうえで、より小さく誠実な一歩を検討する価値はある——
**自分のアカウントに対して行われた操作の監査ログを、管理者でない本人にも見せる**
こと。そうすれば悪意ある Owner は、別の Owner ではなく、影響を受けた本人に
よって気づかれる。

## まとめ

|                             | 推奨                                             |
| --------------------------- | ------------------------------------------------ |
| 1. お知らせのオフライン閲覧 | **完了**（M6a）。取得時刻を必ず表示、E2E で担保  |
| 2. アカウントロック         | 維持。ロックではなく本人に通知                   |
| 3. HTTP 経由のバックアップ  | **完了**（M6a）。Owner + パスワード再入力 + 監査 |
| 4. 書庫の暗号化             | **完了**（M6a）。`--encrypt-to`、鍵は持たない    |
| 5. 通話画面の埋め込み       | **完了**。任意設定、CSP は一つ分だけ動いた       |
| 6. 悪意ある管理者           | 維持。本人に自分の監査ログを見せる               |

四つはやった、二つは残す——残す二つにはどちらも、代わりにやる価値のある、より
小さく誠実な代替案がある。繰り返しの失敗はロックせず本人に通知すること、そして
自分のアカウントに対する操作の監査ログを本人に見せること。

項目 5 は覚えておく価値がある。維持と決めた根拠は、CSP の二つのディレクティブを
一つと読み違えた読解だった。教訓は「CSP にもっと大胆になれ」ではない——**検証
できるだけ詳しく書き残された拒否は、誰かが誤りを見つけられる拒否である** という
ことだ。この文書に残っている四つの理由は、同じやり方で検証したうえで残っている。
